## Summary

The concrete sum-check layer is the path from a declared relation to a verified stage: the claim derives of `jolt-claims-derive`, `ConcreteSumcheck`, `#[derive(SumcheckBatch)]`, `PrepareKernel` and `SumcheckKernel`, the reference kernel `NaiveSumcheckProver`, and the stage driver generated by `impl_stage_prover!`. Its traits are generic in the field and in a relation's id families, and `specs/binary-sumcheck.md` made the batching engine beneath it valid in characteristic 2. Five places in the layer still assume a field where 2 is invertible, or one of the two protocol families defined in the workspace.

1. The fold generated by `#[derive(SumcheckBatch)]` omits the factor `λ_i` that zero extension puts on a member's final claim (notation under Goal). Over a binary field an honest proof ends at `Σ_i c_i λ_i g_i(r_{W_i})` and the fold expects `Σ_i c_i g_i(r_{W_i})`. An honest batch whose members differ in length is therefore rejected unless the discrepancy `Σ_i c_i (λ_i − 1) g_i(r_{W_i})` vanishes, which takes zero evaluations or coefficients, a scale equal to one, or cancellation between members. The same fold is also unsound. It is the endpoint of the sum-check for the constant extension `G(x) = Σ_i c_i g_i(x_{W_i})`, and in characteristic 2 the constant extension of a member shorter than the batch sums to zero over the cube: `g(x) = x`, extended by one dummy variable, has sum one natively and zero when extended. A prover that claims zero for every shorter member and runs the sum-check for `G` honestly is accepted, whatever those members' true sums are. Other claims are rejected except with the usual soundness error over `c_i` and `r`; the batch identity constrains the weighted sum of the claims, not each claim.
2. `ComposedOpeningId`, `VerifierDerivedId` and `VerifierChallengeId` are closed enums with one arm per workspace family, and `ConcreteSumcheck` requires a relation's ids to convert into them.
3. `sample_dense_round`, the round routine of the reference kernels, samples at `F::from_u64(k)` and interpolates with `UnivariatePoly::from_evals`. In characteristic 2 those nodes take two values, and `from_evals` panics for three or more evaluations.
4. `PrepareKernel::prepare` and the stage driver take the witness as `&dyn JoltWitnessPlane<F>`, and `impl_stage_prover!` is private to `jolt-prover`. Its expansion contains a blanket impl of a `jolt-prover` trait for an uncovered type parameter, which the orphan rule rejects in every other crate.
5. `#[protocol(..)]` on the claim derives accepts `jolt` and `field_inline` only.

This spec removes the five assumptions, as five commits of one pull request. It continues the binary-field stack and is motivated by generality: a protocol family defined outside the workspace, over a field of either characteristic, is then declared, proved with the reference kernel and verified with the existing derives and driver. Behaviour of the existing families over the existing fields does not change.

## Intent

### Goal

A protocol family defined in a crate outside the workspace, over a field of characteristic 2, declares its relations, batches and stages with the existing claim derives, `ConcreteSumcheck`, `#[derive(SumcheckBatch)]`, `#[derive(KernelSlots)]`, `NaiveSumcheckProver` and `impl_stage_prover!`, and its stages are proved and verified correctly.

| Part | Change | Path affected |
|---|---|---|
| 1 | The generated fold applies the batch output scale | production: verifier and prover driver |
| 2 | An `External` arm in the three composite id enums | production, type level |
| 3 | Node sampling in the reference round routine | reference tier; the optimised RAM raf-evaluation kernel, which runs the reference round loop |
| 4 | A witness-plane parameter on `PrepareKernel`; `impl_stage_prover!` exported | production, type level; the seam optimised kernels attach to |
| 5 | `#[protocol(ids = path)]` on the claim derives | compile time |

Parts are numbered in commit order. Notation is that of `specs/binary-sumcheck.md`: `n = max_num_vars`; member `i` has batching coefficient `c_i`, window `W_i = [offset_i, offset_i + rounds_i)` and polynomial `g_i`; `r[j]` is the challenge of batch round `j`; `e_i = g_i(r_{W_i})`; the output scale `λ_i` is `F::one()` under constant extension and `∏_{j ∉ W_i} (1 − r_j)` under zero extension.

**Part 1: batch output scale in the generated fold**

```rust
// crates/jolt-sumcheck/src/batch.rs
impl<F: Field> BatchPrelude<F> {
    /// One output scale per member, in member order.
    pub fn member_output_scales(&self, challenges: &[F]) -> Result<Vec<F>, SumcheckError<F>>;
}

// generated by #[derive(SumcheckBatch)]: two new leading arguments,
// the existing five follow in their current order
pub fn expected_final_claim(
    &self,
    batch: &::jolt_sumcheck::BatchPrelude<F>,
    batch_point: &[F],
    /* coefficients, input_points, output_values, output_points, challenges */
) -> Result<F, VerifierError>;
```

- **1.1 Fold.** `expected_final_claim` returns `Σ_i c_i · λ_i · e_i` over the present members in declaration order, where `λ_i` is entry `i` of `batch.member_output_scales(batch_point)`.
- **1.2 Member correspondence.** `begin_batch` pushes one `BatchMember` per present member in declaration order and the fold visits the present members in the same order, so an absent `Option` member takes no entry in either. If the number of folded terms differs from the number of scales, the fold returns `VerifierError::StageClaimSumcheckFailed`.
- **1.3 One owner of the factor.** `member_output_scales` validates the prelude's dimensions and then the challenge count, once, and selects the padding rule once. `member_output_scale` is built from the same validation and the same window product, and keeps its error precedence: dimensions, then `RoundMemberIndexOutOfRange`, then `WrongNumberOfRounds` (`batch.rs:135–147`). Generated code contains no padding arithmetic and no test of the characteristic.
- **1.4 Rule selection.** `PaddingRule` gains a crate-private predicate for zero extension, `F::from_u64(2).is_zero()`. `PaddingRule::for_field` is expressed through it and inverts 2 only when the predicate is false, which is the selection of `specs/binary-sumcheck.md` invariant 1. Neither scale method performs an inversion.
- **1.5 Callers.** The generated `verify_clear` passes the prelude from its own `begin_batch` and the point returned by its own round verification. The body of `impl_stage_prover!` passes the prelude it proved against and `ProvedBatch::challenges`. There is no other caller.
- **1.6 `expected_output` stays native.** It is `g_i(r_{W_i})` under both rules. `ConcreteSumcheck` does not change.
- **1.7 Errors.** A failure of `member_output_scales` maps to `VerifierError::StageClaimSumcheckFailed` carrying the error's message.

  - Its `From` conversions into each composite enum are injective per id kind.

  These are soundness requirements. `resolve_member_opening` trusts `TryFrom`, and the generated resolver takes the first member that resolves an id (`or_else`, `crates/jolt-verifier-derive/src/lib.rs:816–833`). A family that reuses a `family` string, collapses two ids or accepts a foreign id makes alias validation compare the wrong claims without an error.
- **2.5 Not on the wire.** Composite ids are not serialised and not absorbed into a transcript.

**Part 3: node sampling in the reference round routine**

`pub(crate) fn sample_dense_round<F: JoltField>` in `crates/jolt-kernels/src/reference/naive.rs` keeps its signature and its two callers (`naive.rs:342`, `reference/bytecode_read_raf.rs:801`). `jolt_poly::lagrange::validate_nodes` becomes `pub`, so the distinctness rule keeps one owner.

- **3.1 Nodes.** For a relation of degree `d` the routine samples at `d + 1` nodes: node 0 is `F::zero()`, node 1 is `F::one()`, node `k ≥ 2` is `F::from_u128_checked(k)`. This is one path for every field. `JoltField` supplies `CanonicalEncoding`; a `Field` without it cannot instantiate the routine, before or after this change.
- **3.2 Message.** The round polynomial is `UnivariatePoly::new(interpolate_nodes_to_coeffs(&nodes, &evals)?)` with `jolt_poly::lagrange::interpolate_nodes_to_coeffs`: exactly `d + 1` coefficients, trailing zeros retained.
- **3.3 Existing fields.** Where `from_u128_checked(k)` equals `F::from_u64(k)` for `k ≤ d`, which holds in the workspace's prime fields whenever the field has more than `d` elements, the nodes are the integers `0..=d`. The interpolant through `d + 1` distinct nodes is unique and both constructions return exactly `d + 1` coefficients, so the message equals, coefficient for coefficient, the one `UnivariatePoly::from_evals` returns.
- **3.4 Order of checks.** Before the first call of `term`:
  1. `degree.checked_add(1)`; failure returns `SumcheckError::DegreeOverflow { degree }`.
  2. All `d + 1` nodes are built and passed to `validate_nodes`. A node that does not exist (`from_u128_checked` returns `None`) or a repeated node returns `SumcheckError::IntegerDomainNotDistinct { domain_size: d + 1 }`.

  The samples, the running-claim check and the interpolation follow. A `LagrangeNodesError` from the interpolation maps to the same `IntegerDomainNotDistinct` and cannot occur after step 2. For `d ≥ 1`, which the running-claim check already presupposes, and `d + 1` nodes and samples that can be allocated, the routine returns a polynomial or a typed error and does not panic. Degrees can depend on geometry (`crates/jolt-claims/src/protocols/jolt/relations/ram/ra_virtualization.rs:60–61`, `instruction/read_raf.rs:81–82`), so step 2 is a runtime check and not a property of a relation type.
- **3.5 Running claim.** The check `s(0) + s(1) == previous_claim` is unchanged and uses the samples at nodes 0 and 1.

**Part 5: `#[protocol(ids = path)]`**

```text
#[protocol(jolt)] | #[protocol(field_inline)] | #[protocol(ids = <path>)]
```

- **5.1 One emitter.** `parse_namespace` builds the existing `Namespace` value from `<path>`: `opening_id = <path>::OpeningId`, `relation_id = <path>::RelationId`, `virtual_polynomial = <path>::VirtualPolynomial`, `committed_polynomial = <path>::CommittedPolynomial`, `challenge_id = <path>::ChallengeId`, `allows_advice = false`. The emitters are not changed.
- **5.2 Contract of the module at `<path>`**, stated in the crate docs. Items a deriving type does not use need not exist.
  - `RelationId`, with a variant `Rel` for every `#[relation(Rel)]` and every `from = Rel`.
  - `OpeningId: PartialEq + Debug`. The generated resolvers compare ids with `==` (`crates/jolt-claims-derive/src/lib.rs:518`, `539`, `549`, `679`, `697`), and the output constructor returns `::jolt_claims::MissingOpeningValue<OpeningId>`, whose parameter is bounded by `Debug` (`crates/jolt-claims/src/claim_data.rs:47`).
  - For a virtual leaf, `VirtualPolynomial` and `OpeningId::virtual_polynomial(VirtualPolynomial, RelationId)`. The leaf's attribute and field type fix the variant and its arity: `VirtualPolynomial::V` for a scalar field, `V(usize)` for a `Vec` field (the element index), `V(payload)` for a leaf whose attribute carries a payload.
  - For a committed leaf, `CommittedPolynomial`, with `V` or `V(usize)` by the same rule, and `OpeningId::committed(CommittedPolynomial, RelationId)`.
  - For `#[derive(SumcheckChallenges)]`, `ChallengeId: PartialEq` (`lib.rs:811`) and `ChallengeId: From<S>` for the type `S` of each path a field's attribute names (`lib.rs:809`).

  These are the derives' requirements. Using the derived structs as a relation's claims adds the bounds of `ConcreteSumcheck` (`crates/jolt-verifier/src/stages/relations.rs:104–112`), which the crate docs point to and do not restate: `Debug + Copy` on the relation id, `Copy + Ord + Debug` and the composite conversions on the opening id, `Copy + Debug` and the composite conversion on derived and challenge ids.
- **5.3 Path tokens.** `<path>` is emitted verbatim and resolves at the derive site.
- **5.4 Existing namespaces.** `jolt`, `field_inline` and an absent attribute produce the token streams they produce today.
- **5.5 Diagnostics.** Advice leaves stay rejected under `ids = ..` with the existing message. A duplicate attribute, a key other than `ids`, and a value that is not a path are compile errors spanned on the attribute. The unknown-namespace message lists the three forms.

### Non-Goals

1. `verify_zk`, BlindFold and the committed recorder over a field of characteristic 2. They are unchanged; the doc comment of the generated `verify_zk` gains one sentence saying it assumes constant extension.
2. Univariate skip in characteristic 2.
3. Jolt's own relations, witness or kernels over a binary field, and any optimised kernel for a hosted family.
4. A `KernelError` variant for witness errors of a hosted family. `KernelError::InvalidGeometry` and `InvariantViolation` carry them.
5. Moving the stage driver out of `jolt-prover`, and exporting the internals of `jolt_kernels::optimized` or the parity harness.
6. Replacing the panicking `BatchPrelude::new` call in the generated `begin_batch`.
7. Any change to proof encoding, transcript labels or `ConcreteSumcheck`.
8. Runtime enforcement of the hosted-family contract of 2.4.
9. A permanent benchmark for stage verification, a stage driver or the RAM raf-evaluation kernel, and a consumer package or CI lane for the exported macro.

## Evaluation

### Testing Strategy

Existing suites pass with no edit beyond the adaptations of G1 and are the evidence for it: the `jolt-verifier` fixture suites, `crates/jolt-prover/tests/{e2e_matrix, engine_twins, zk_e2e}.rs`, the twin tests in `crates/jolt-prover/src/stages/drivers.rs`, the tests of `naive.rs`, and the lockstep parity tests under `crates/jolt-kernels/src/optimized`. The parity tests compare round messages after trimming trailing zeros (`optimized/testing.rs:251–259`), so they pin the polynomial of part 3 in odd characteristic but not a member's coefficient count. The count is pinned by the trailing-zero criterion of part 3 and by the exact comparisons at `optimized/instruction_input.rs:580–582`.

Expected values in new tests come from definitions: sums taken directly over the cube, `Polynomial::evaluate` on explicit tables, products over the challenges outside a window written in the test, literal coefficients, and literal ids. No test computes its expectation with `member_output_scale`, `member_output_scales`, `sample_dense_round`, `interpolate_nodes_to_coeffs` or `UnivariatePoly::from_evals`. Transition evidence belongs in the pull request and is not committed: over `Fr`, for degrees 1 to 7, the coefficient vectors of the new routine equal those of `from_evals` on the same samples.

New permanent tests are scoped to signals no existing test gives:

- The binary driver fixture of part 1 isolates the fold from interpolation: it has degree 1 and its own kernel, so it does not depend on part 3. Its absent-member case is the one that catches a shift between the scale vector and the folded members, since over `Fr` every scale is one. `ToyDelta` cannot serve as its head-aligned member: its `expected_output` inverts `F::from_u64(1 << HEAD_PAD)`, which is zero in characteristic 2, and `HeadDensePrepare` builds a table at the padded scale. `ToyDelta`, `ToyHeadSumchecks` and `HeadDensePrepare` stay as they are.
- The end-to-end test is an integration test because only a separate crate exercises the orphan rule, `#[macro_export]` and the absolute paths of the expansion. An in-crate test would pass with an expansion that is illegal in every other crate. It replaces the part-4 fixture, whose success signal it contains.
- An integration test of `jolt-prover` is compiled with the package's features, so it cannot observe an expansion-site `cfg(feature = "allocative")`. Every token of an expansion that does not come from the invocation comes from the bodies of the four macros, so the source assertion of part 4 states the property exactly.
- The id tests of part 2 exercise the conversions of the toy families. They do not enforce 2.4 for another family; its obligations stay with its author.

Tests over binary fields enable the `binary` feature of `jolt-field` through dev-dependencies of `jolt-prover` and `jolt-kernels`. No production feature set changes.

### Performance

The target is no material regression for the existing families over prime fields. The parts add this work on existing paths:

| Part | Where | Work added |
|---|---|---|
| 1 | verifier and prover driver, once per batch after the round loop | One dimension validation linear in the member count, one zero test of `F::from_u64(2)`, one `Vec<F>` with one entry per member, one multiplication by `F::one()` per member. |
| 2 | type level | No operation is added and no algorithm changes; two enums grow. On a 64-bit target with rustc 1.95.0, measured on layout-equivalent declarations: `ExternalId` 24 bytes; `ComposedOpeningId` 32 → 32; `VerifierDerivedId` 24 → 32; `VerifierChallengeId` 2 → 32. Enum layout is not fixed across targets or compilers. Composite ids key claim maps (`crates/jolt-kernels/src/optimized/spartan_outer.rs:1457`, `spartan_product.rs:715`), are copied in stage 8 (`crates/jolt-verifier/src/stages/stage8/verify.rs:171`) and sit in error values, whose layout can grow with them. They are handled per opening, never per row or per round. |
| 3 | every call of `sample_dense_round` | See below. |
| 4 | type level | None. The plane is a type parameter resolved at compile time; the driver is monomorphised per batch and kernel source as today; `PrepareKernel` stays behind the same `Box<dyn ..>` per slot, called once per member per stage. |
| 5 | compile time | None. |

Part 3 is on a production path. `JoltBackend::optimized()`, which the SDK selects (`jolt-sdk/src/host_utils.rs:361`), installs `OptimizedBackend` for `RamRafEvaluation` (`crates/jolt-kernels/src/optimized/mod.rs:125`). That kernel wraps `NaiveSumcheckProver::new_with_table_rounds` in `RamAddressKernel` (`optimized/ram_raf_evaluation.rs:60–67`), which forwards each active address round to the reference round loop (`optimized/read_write.rs:145–150`). `sample_dense_round` therefore runs once per active RAM address round, `ram_log_k` times per proof, at `d = 2`. Per call:

| | `from_evals` | nodes and `interpolate_nodes_to_coeffs` | at `d = 2` |
|---|---|---|---|
| Inversions | `d` | `d + 1` | 2 → 3 |
| Heap allocations besides the sample vector | `d + 3` | 4: the nodes and three working vectors | 5 → 4 |
| Node construction and validation | none | `d − 1` calls of `from_u128_checked`; distinctness checked twice, `d(d + 1)/2` comparisons each | 1 call, 6 comparisons |
| Multiplications | `O(d²)` | `O(d²)` | |

The sampling pass, `d + 1` evaluations of the summand over the `half` rows of the round, is unchanged.

Evidence, reported in the pull request from the base commit and from the branch on one machine:

1. `cargo bench -p jolt-eval --bench prover_time_fibonacci` and `cargo bench -p jolt-eval --bench prover_time_secp256k1_ecdsa_verify`, which run the optimised backend (`jolt-eval/src/guests/mod.rs:47–53`). For each: the workload and its trace length in cycles, baseline and candidate time, the spread Criterion reports for each, and ns per cycle.
2. The RAM raf stage in isolation, through the profile harness: `cargo run --release -p jolt-prover --features profiling -- profile --name fibonacci --format chrome --backend optimized`, three runs a side, reporting `jq '.spans."RamRafEvaluation::prove_round"' benchmark-runs/latest_modular_fibonacci_16_optimized/summary.json`. Whole-prover times cannot resolve a change of one inversion per address round; this span can.
3. `size_of` of `ExternalId`, `ComposedOpeningId`, `VerifierDerivedId` and `VerifierChallengeId` on the real declarations, before and after.

No benchmark is added to the workspace, and no `jolt-eval` objective is added or expected to move.

Part 4 is the shape a later optimised kernel of a hosted family depends on. `P::Ref<'_>` is chosen by the family, so a plane can hand `prepare` packed words or borrowed slices; nothing in `PrepareKernel`, `SumcheckKernel` or the driver requires a dense table of field elements. What a kernel keeps for the round loop is bounded by 4.1.

The member claims that `prove_batch` returns already carry the output scale (`specs/binary-sumcheck.md` invariant 5), so after part 1 the driver's self-check compares like with like under both rules. Over a binary field the engine hands each member its native claim inside its window, so `NaiveSumcheckProver` serves a head-aligned member with no adjustment.

### Alternatives Considered

1. **Fold the scale into each relation's `expected_output`.** Rejected: the scale depends on the batch length and the member's window, which a relation does not know.
2. **Call `member_output_scale` once per member from generated code.** Rejected: each call validates the whole prelude again, quadratic in the member count, and the method as it stands inverts 2 on every call to select the rule.
3. **A second generated fold that applies the scale.** Rejected: two folds, and the unscaled one does not check shorter members over a binary field.
4. **An arm per hosted family, behind a feature, carrying the family's id types.** Rejected: it moves a family's vocabulary into the workspace and adds an enum arm, a feature and match arms per family.
5. **Make the layer generic in the composite id type.** Rejected for size: `VerifierError` is named in 107 files under `crates/` and `KernelError` in 82, and both would gain a type parameter.
6. **Branch on the characteristic in `sample_dense_round`, keeping `from_evals` where 2 is invertible.** Rejected: two definitions of the round message for no observable difference (3.3), and the branch would be the only test of the characteristic outside `PaddingRule`. The cost of the single path is measured instead (Performance).
7. **Export `impl_stage_prover!` unchanged.** Does not compile outside `jolt-prover`: `impl<F, B> KernelSource<F, $batch<F>> for B` implements a foreign trait for an uncovered type parameter (E0210).
8. **Keep `StageProver<F>` and bound `prove` by `where Self: PrepareMembers<F, B>`.** Does not compile: the where-clause brings `Self: StageProver<F>` into the parameter environment, and the associated types in the method signature no longer normalise to the impl's types.
9. **A defaulted unsized parameter, `PrepareKernel<F, R, W: ?Sized = dyn JoltWitnessPlane<F>>` with `witness: &W`.** Rejected: in a default the object lifetime bound is `'static`, so every existing caller would have to pass a `'static` witness object (E0521 at the call), and a plane that is not a single reference cannot be expressed.
10. **A third hard-coded namespace per family in `jolt-claims-derive`.** Rejected: the derive would name crates outside the workspace.
11. **Keep the `$crate::driver::__stage_*!` paths and make the module re-exports of the helpers public.** Rejected: `#[macro_export]` already places the helpers at the crate root, and a second public path to hidden items is surface with no user.
12. **A consumer package with its own feature set to check the hygiene of the expansion,** as `crates/jolt-sumcheck/tests/external-consumer` does for the engine. Rejected: the property is syntactic, and the source assertion of part 4 states it without a package and a CI lane.

The guest fixtures run only under `prover-fixtures`; a run without it does not exercise them. The `fuzzing` lane is the only one that compiles the arm at `blindfold/mod.rs:472`, and no CI job builds it.
