03 · How the GPU actually works

The M5 Max, mechanically, and how we read it blind

Requested explainer. What the machine is, what the four limiting regimes mean physically, and how each is identified from the instruments this host actually has.

The machine

The M5 Max GPU is a tiled array of GPU cores sharing one LPDDR memory system and a system-level cache (SLC) with the CPU — unified memory: same silicon carries CPU loads and GPU streams, so they can starve each other (measured: concurrent CPU field-mul cuts GPU streaming 357→162 GB/s, −55%, while the CPU side loses 45%).

Work arrives as threadgroups, dispatched from command buffers. Each core executes threads in SIMD-groups of 32 in lockstep. A core keeps many SIMD-groups resident simultaneously and switches between them every cycle — that residency is occupancy, and it is the only latency-hiding mechanism: when one SIMD-group stalls on a memory load, another issues. Residency is capped by whichever runs out first: registers per thread, threadgroup memory, or simply too few threads in the dispatch.

Measured roofs for this silicon (wave-1 microbenches): 11.30 Gmont-mul/s compute; 485 GB/s best isolated stream, 357 GB/s sustained under contention; empty command-buffer round trip 133.8 µs.

The four regimes

Reading it blind

This host has no xctrace/Instruments; public Metal exposes only timestamp counters — no ALU-occupancy, SIMD-utilization, cache-miss, or DRAM-byte counters. So regime identification triangulates: ioreg device-active samples (~4/s) for idle windows, command-buffer GPU timestamps for queue/execution split, controlled roof microbenches for ceilings, thread-scaling sweeps for occupancy, and co-run contention probes for fabric sharing. A multi-second exact-zero sample run rejects device occupancy; a high GPU% does not prove ALU saturation — this is exactly the relabeling the audit was checked for and did not commit.

Our stages on the taxonomy

  • st0 — fabric contention + ambient clock. GPU commit streams while the hoisted CPU record walk (13.3 s span) shares the memory system. The ±5 s bimodality survives with the walk removed (solo commit 3.8→22.5 s, constant utime) ⇒ device power/clock state, unfixable in-process. Contention is real but secondary and tracks co-runner residency, not intensity.
  • st3, st7 — host-serial, now largely cut. Single CPU functions covering sampled-zero windows; both got device or parallel rebuilds in wave 2.
  • st4 — host/device ping-pong. Not one big gap but a per-round alternation (message → host scan/alloc → bind), 4.8 s held-zero across 51 CBs. The wave-3 lane owns the W2B device-prepare salvage (−64.6% cool @2²⁵ in isolation) plus wait/scan fusion.
  • st5 — device-saturated, regime unresolved. 77.6% active, InstrReadRAF d=6 rounds dominate. ALU vs bandwidth genuinely unknown without counters; the wave-3 lane's harness must report achieved mul/s against the 11.30 G roof.
  • st6b — was allocation/sync, not bandwidth. Its dense streams cost ≈0.3 s at roof against a 16.35 s stage; the mass was three serialized synchronous adoption materializations writing 28.5 GiB of fresh pages. Deferred+fused adoption (one detached CB at T/16) took it to 7.02 s. Residual: gather arithmetic, per-round waits, shrinking-tail occupancy.
  • st8 — ALU/occupancy. 86.6% active, Miller-loop pairing math near the compute roof, insensitive to memory soak, and per-pair cost collapsing until 4k–8k threads are exposed ⇒ dispatch geometry, not bytes. Wave-3 lane on occupancy/packing.

06 · Honest verdict

Was the reporting agent bullshitting?

Verdict
No fabrication, real measurement discipline, sloppy presentation. Every number survives independent recomputation from raw artifacts, conventions were declared, and the wave-1 self-correction (withdrawing the stage-4 estimate) was honest. But the user-facing HTML invented four of nine stage subjects instead of copying them from its own source report, promoted the one next-bet its source ranked lower — which died within hours — and left four redundant files behind.
Basis: raw monitor JSON recompute · stage source code · member→span trace map · lane reports · wave-2 certification
  • Right: the core thesis (“not one roof; host serialization + fabric contention, not missing dispatches”) — wave-2 outcomes confirmed it. Zero-run ledger, launch-ceiling math, roofs, contention probes: all reproducible. Refusing to relabel ioreg% as ALU saturation was correct rigor.
  • Sloppy: stage subjects written from a generic zkVM pipeline memory rather than the evidence one directory over; st0 promoted to bet #1 against its own source's ranking; st6b's 2–5% estimate low by ~3×; four artifact files where one belongs.
  • Misleading (mildly): only the labels. Anyone navigating by protocol member — which is how the wave-2/3 lanes actually work — would have been sent to the wrong code for st4, st5, st6b, and st7. The campaign avoided damage because the lanes worked from the journal and lane reports, not the HTML.
